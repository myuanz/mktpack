# 金融时序存储与数据适配器

## 背景

最初的基本目标是自描述的 MKP 文件编码解码器，提供超高级别压缩的 kline，并完成了 binance 的 port，通过`mkt binance`命令前缀提供下载功能，mkp 文件写出到
```
{symbol}/yyyy.mkp
{symbol}/yyyymm.mkp
{symbol}/yyyymmdd.mkp
```
无索引文件，自然月结束时，将自然日重新编码和压缩成一个单独的月文件，年结束时变成单独的年文件，我将这种规则叫作 ymd 归档，保存方式叫作松散目录. 

后来为了将零散文件打包为有尺寸上限的文件(从 1 开始的 mkt.data.{N} 文件)，基于 SQLite 构建了数据集索引文件，用来查询特定的数据在哪个分卷里，分卷文件里保存了 mkp 的 blob，可以通过 id 查询，此时有了`mkt package`. 随后为了将资金费率结算记录和交易所信息加入，区分了「mkp时序数据、sqlite时序数据、非时序数据」. 

后来开始适配 ctp tick，一个品种一天的 tick 数据就已经非常大，月内数据不适合再重新编码压缩，因此我选择了复用打包规则，将每个交易日的 mkp blob 插入 sqlite，sqlite 文件命名上仍然保持 ymd 规则. 于是数据组成为这样: 

两种数据: 
1. 时序数据
2. 非时序数据，例如品种信息

时序数据有两种格式: 
1. mkp 时序压缩，例如 kline、tick
2. plain SQLite 行储存，例如资金费率历史

mkp 时序压缩数据有两种载体:
1. 直接的 mkp 文件
2. SQLite BLOB，将 mkp 文件数据流作为 blob 保存到 SQLite

此时打包与否已经区别不大，我时常随便修改格式，因为代价无非是重新从原始数据导入. 

后来格式很好用，开始有了下游用户，我还负责定期给下游用户分发更新的 tick 数据，分发分成两个阶段: 1) 初始化阶段，用户下载一份检查点. 2) 增量更新阶段.

增量更新时我希望尽量不要大范围修改打包文件，因为 DELETE 会给 sqlite 带来空洞，INSERT 也可能不连续，幸运的是，得益于巧妙的并行读入，按(symbol, time)保存数据和(time, symbol)保存的数据读取速度差异在1倍之内，于是我可以将不会再变化的 mkp 块(例如 ctp tick 日包)写入到最后一个 `mkt.data.{N}`，而可能会重新编码压缩的数据(例如币安的分钟kline)，我将其写入`hot.data.{N}`. 

我担心未来更变某些格式无法直接正确适配到客户端的旧数据，因此我引入了严格版本要求的升级包，内含数据、升级脚本、要求的上一个版本，客户端基本上只需要 merge，但偶尔可能会需要执行特殊的升级脚本，相关命令放在`mkt merge`

基于工程审美: 
- 读取代码不应该被不同的 port 侵入
- 这个库应当提供一个 Python 绑定，并发布到 pypi/mktpack
- Python 侧应当尽量薄，只提供接口和类型签名
- 所有能输入零散文件目录的地方，都应该能输入打包目录，所有能写出到零散文件目录的接口，都应该能写出到打包目录

## 国内期货 tick

执行 `mkt ctp-futures import` 读取 ctp-mirror 根目录下 `nfs_rq*/tick/future` 的完整 ZIP。源文件名末尾的 `YYYYMMDD` 是交易日，不使用记录内的 `tradingdate`。可选的 `basicinfo/future_instrument` 快照提供标准合约代码、存续日期、最小变动价位和合约乘数。合约目录使用标准代码，不添加交易所前缀。

| tick 组字段 | 来源与含义 |
|---|---|
| `time`、`trading_day`、`symbol` | `trade_timestamp` 的 UTC 毫秒、源文件名日期、标准合约名 |
| `last_price/open_price/highest_price/lowest_price/close_price` | 最新、开、高、低、收 |
| `settlement_price/pre_settlement_price/pre_close_price/upper_limit_price/lower_limit_price` | 当前及前日参考价、涨跌停价 |
| `volume/turnover/open_interest/pre_open_interest` | 累计成交量、累计成交额、持仓量和昨持仓 |
| `bid_price1…5/ask_price1…5/bid_volume1…5/ask_volume1…5` | 五档买卖价格和数量，保留零档位 |

带浮点尾差的价格、成交额与持仓量按 binary64 最短十进制归整，同合约价格列使用共同尺度和 GCD。各交易日独立编码，保留重复时间戳和源顺序。

CTP tick 的逻辑期间为交易日：

```text
tick/AP2701/20260102.mkp
```

月份结束后，每个合约新建月份卷：

```text
tick/AP2701/202601.data
```

年份结束或合约封存时，月份卷重写合并为 `2026.data`。日级索引始终保留，归档只改变载荷位置。

只考虑完整源包，不处理跨来源拼接、部分到达或替换。跳过文件名在交易日前带 `_F` 后缀的源包。空库回灌按年组织待写数据，直接写入相应的年卷、月卷和日文件。增量导入按源包写日文件，随后归档。

导入只会在收盘后由单个进程独占执行，因此不考虑任何并行、锁、断电安全。

另提供 `mkt ctp-futures import --profile <文件>` 以写入导入、编码、索引和归档各阶段的耗时与数据量，用于吞吐分析。

## 统一写入、打包

所有的索引文件里，应当有一张 `__meta__` 表，记录 `port`、`version`，新建或打包时默认写入当天 UTC+8 日期 `YYYY.MM.DD`，如果是打包后的，则还要有一个 `max_file_size`，未手工指定时默认 8 GiB，允许不同 `port` 决定打包、写入与归档的冷热策略，从源头避免 SQLite 空洞. 

- **松散目录**：由文件系统负责为 mkp 文件分级的目录
- **打包目录**：`ctp-futures` 等按日独立分块的数据直接写入并尾部追加至未满 `mkt.data.N`；`binance` 将当年未封存数据隔离在热卷 `hot.data.1..M`，跨年后由 `mkt compact` 封存至末尾冷卷并清理旧热卷；

## 增量升级

下游使用打包数据的用户，可以通过 `mkt merge` 合并新版本的数据，合并的基础结构是如下格式的 zip 文件: 
- 根目录含 `meta.json`，含 `to`、`from` 及可选 `script`，`script` 显式指定包内更新脚本路径
- 含 `data/` 目录，其下是 `mkt package` 包装出来的按 `[start,end)` 筛选出来的数据
- 可选更新脚本（`script` 字段），用于处理格式变化、索引迁移等不容易考虑周全的事务，SQLite 时序表的增量更新也可经此. 

该接口有两种使用方式: 
1. 传入多个 zip 文件，程序会同时提取所有 `meta.json`，构建升级计划
2. 传入一个指向 `manifest.json` 的 `http(s)://` 文件地址，其顶层包含 `latest` 目标版本号与 `packages` 数组，汇总各升级包的 `meta.json` 及对应的下载 `url`、`size`、`sha256`。

## Python 接口与 CLI

如上的数据集维护功能都提供 Python API，除此之外，最重要的查询与单文件接口包含: 

- 对数据集和组的 `describe()`，以及按区间列出实际有记录品种的 `symbols()`
- 对时序组 `read()`，函数支持单个或多个 symbol、时间范围和列投影，按 `(symbol, time)` 顺序返回 Arrow Table。查询在 SQLite 中筛选组、合约和时间，流式读取分卷载荷并全核并行解码直写目标列缓冲。
- 单文件调试接口 `mktpack.raw`（`raw.write`、`raw.read`、`raw.info`），用于单文件读写与调试。

原生 CLI `mkt` 的 `--root` 为全局参数，省略时默认使用当前目录（若当前目录已有 `mkt.sqlite`）。下载器在 TTY 下使用固定工作槽显示进度条，非 TTY 输出阶段摘要；维护与查询命令输出结构化 JSON 供脚本消费。

## MKP 基础格式与元数据表

### 文件布局与列编码

所有整数采用小端序。MKP 文件依次包含：

| 部分 | 编码 |
|---|---|
| 文件标识 | 8 字节 `MKP\r\n\x1a\n\0` |
| 头部长度 | uint32，表示后续 JSON 的字节数 |
| 头部 | UTF-8 JSON |
| 载荷 | 各列按 `columns` 顺序存放编码流 |

头部保存 `version/rows/time_column/first_time/last_time/symbol/metadata/columns`（当前版本为 1，空表首末时间为 null）。每列保存 `name/type/scale/factor/transform/first/mode/bits/raw_size/size`。数值类型为 `timestamp/integer/real`（读取器兼容存量文件的 `decimal` 标签），列值使用 int64，实际数值为整数乘以 `10^-scale`，查询时 `real` 列输出为 Arrow `float64`。时间为 UTC 毫秒。`symbol` 是文件级常量，查询时展开为 Arrow `dictionary<int32, string>` 逻辑列。

编码器按 schema 声明 `scale_group` 和 `prediction`：同一尺度组统一十进制尺度后计算共同 GCD，其余列计算自身 GCD，解码后乘回 `factor`。支持的整数变换：

| transform | 含义 |
|---|---|
| `constant` | 全列等于 `first`，无载荷 |
| `direct` | 直接保存归一化整数 |
| `changes` | 保存变更点的行距和变化量 |
| `delta` | 以前一行为预测值 |
| `reference` | 以同行指定列为预测值 |
| `level_quantity` | 以前一行同侧同价位数量为预测值 |
| `trade_value` | 以上一累计额加价格、成交量差和合约乘数推算累计额 |
| `ratio_1000` | 保存参照列的千分比量化值（`q = round(1000 × B / V)`，范围 0–1000） |

变换残差经 ZigZag 映射为 uint64，尝试 `mode=0`（位平面）与 `mode=1`（字节平面）两种排列并以 Zstd level 9 压缩，保存较短者。列投影读取时自动补充预测依赖列，恢复请求列后丢弃仅用于预测的列。

### 载体与数据集元数据表

MKP 载体包括直接文件和 SQLite BLOB（卷内表 `CREATE TABLE blob(id INTEGER PRIMARY KEY, bytes BLOB NOT NULL)`，BLOB `id` 等于 `__timefile__.id`）。`mkt.sqlite` 系统表使用 `__名称__` 格式：

| 表 | 字段与用途 |
|---|---|
| `__meta__` | 数据集级键值元数据（`key TEXT PRIMARY KEY, value TEXT NOT NULL`），保存 `port`、`max_file_size`、`version` 等；查询与校验层不依赖本表 |
| `__group__` | 数据组的 `id`、`name`、`kind`、`schema`、`storage`、`location`、`table_name`、`time_column`、`symbol_column` |
| `__symbols__` | 品种字典 |
| `__volumes__` | SQLite 载体的唯一 `path` |
| `__timefile__` | MKP 数据流的组、品种、`period`、首末时间、行数和可空 `volume_id`，以 `(group_id,symbol_id,period)` 为唯一键 |
| `__sqlite_partitions__` | SQLite 时序实体表的时间分区、载体、行数和首末时间 |

来源状态表按适配器区分：CTP 使用 `__ctp_futures_series__`、`__ctp_futures_files__`；Binance 使用 `__binance_datavision_paths__`、`__binance_datavision_templates__`、`__binance_datavision_files__`、`__binance_datavision_scans__`、`__binance_rest_funding__`。

## 构建与分发

构建采用 C++20、CMake、CPM 固定版本依赖、nanobind 与 scikit-build-core；Python 3.12+ 通过 uv 管理 `pyproject.toml` 与 `uv.lock`。使用 CPython 3.12 Stable ABI（`cp312-abi3`）通过 `cibuildwheel`（复用主机 CPM 缓存）与 MinGW 交叉编译构建 Linux / Windows wheel，并随 wheel 提供原生 `mkt` 可执行文件。`justfile` 提供开发环境、CLI 构建、测试及各平台 wheel 构建入口。
